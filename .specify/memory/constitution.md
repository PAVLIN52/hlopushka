# Конституция проекта «Хлопушка»

Хлопушка — канбан-трекер задач для видеопродакшна (аналог YouGile). Курсовой проект по
дисциплине «ООП» (2 курс, ИСИТ). Главная цель проекта — показать в рабочем приложении
принципы и технологии из лабораторных работ. Поэтому ООП-требования ниже обязательны
наравне с функциональностью.

## Core Principles

### I. Выделенное ООП-ядро

- Учебная ООП-часть MUST лежать отдельно в `backend/src/core/` с подпапками `exceptions/`,
  `collections/`, `iterators/`, `patterns/`.
- Ядро MUST NOT зависеть от NestJS, Prisma, Socket.IO и других инфраструктурных библиотек.
  Оно состоит из чистого TypeScript, а модули в `backend/src/modules/` используют ядро через
  интерфейсы.
- Каждый класс ядра MUST иметь юнит-тесты, которые запускаются без БД и сети.

**Обоснование:** ядро показывают на защите. Его нужно открыть, прочитать и проверить
отдельно от инфраструктуры.

### II. Обобщённое программирование (дженерики)

- Шаблоны классов из лаб MUST быть реализованы как дженерики TypeScript. Минимальный
  набор: `Repository<T>`, `PriorityQueue<T>`, `LinkedList<T>`.
- Свои коллекции MUST использоваться в реальной логике приложения (очередь задач по
  приоритету/дедлайну, история команд и т.п.), а не лежать мёртвым кодом.
- Тип `any` в ядре MUST NOT использоваться. Где нужно, применяются ограничения
  (`T extends ...`) и `unknown`.

**Обоснование:** дженерики — прямой аналог шаблонов C++ из лаб. Использование в живом коде
доказывает, что они нужны.

### III. Единая модель исключений (NON-NEGOTIABLE)

- Все прикладные ошибки MUST выбрасываться как `CustomException` (наследник `Error`) или его
  наследники: `NotFoundException`, `ValidationException`, `AccessDeniedException`.
- `CustomException` MUST хранить сообщение, значение, вызвавшее ошибку, и код ошибки.
- Преобразование в HTTP-ответ MUST выполняться в одном месте — глобальном exception filter
  NestJS (`NotFound` → 404, `Validation` → 400, `AccessDenied` → 403, прочие → 500).
- Выбрасывать «голый» `Error` или строку в прикладном коде MUST NOT.

**Обоснование:** один предсказуемый формат ошибок для API и фронтенда. Иерархия
демонстрирует наследование и полиморфизм.

### IV. Детерминированное освобождение ресурсов

- Ресурсы (файловые потоки, процессы FFmpeg, соединения с Redis/S3, временные файлы) MUST
  освобождаться через `try/finally` или хуки жизненного цикла `onModuleDestroy` /
  `onApplicationShutdown`.
- Каждый класс, владеющий ресурсом, MUST иметь явный метод освобождения (`dispose()` /
  `close()`).

**Обоснование:** в TS нет умных указателей, память управляется сборщиком мусора. В отчёте
этот принцип показывается как аналог RAII.

### V. Паттерны проектирования по назначению

Каждый паттерн MUST решать конкретную задачу домена:

| Паттерн | Где применяется |
|---|---|
| Command | перемещения карточек канбана с undo/redo |
| State | этапы задачи и допустимые переходы между ними |
| Observer | уведомления об изменениях через WebSocket (Socket.IO) |
| Strategy | пресеты экспорта и генерации прокси/HLS-видео |
| Factory Method | создание типов задач: съёмка, монтаж, цвет и др. |
| Proxy | ленивое/кешированное получение метаданных видео |
| Singleton | логгер |

- Реализации паттернов MUST лежать в `core/patterns/` (или опираться на интерфейсы оттуда) и
  быть подписаны в коде комментарием с названием паттерна.
- Недопустимые переходы State MUST выбрасывать `ValidationException`.

**Обоснование:** паттерн, привязанный к реальной задаче, проще защитить и объяснить.

### VI. Итераторы с контрактом

- В ядре MUST быть общий интерфейс `IIterator<T>` (как минимум `hasNext()`, `next()`,
  `reset()`) и не меньше двух реализаций. Например: по этапам вперёд/назад, по комментариям
  в порядке таймкода, по задачам в порядке дедлайнов.
- Вызов `next()` на пустой коллекции или после конца MUST выбрасывать `CustomException` с
  понятным кодом.
- Итераторы MUST по возможности реализовывать `[Symbol.iterator]` для `for...of`.

**Обоснование:** это требование текущей лабораторной. Исключения на границах связывают
итераторы с принципом III.

### VII. Документируемость для отчёта и защиты

- Публичные классы и методы ядра MUST иметь JSDoc-комментарии на русском языке.
- Для каждой фичи, затрагивающей ядро, план (`plan.md`) MUST содержать фрагмент
  UML-диаграммы классов. Для ключевых сценариев (перемещение карточки, загрузка видео,
  комментарий по таймкоду) MUST быть диаграмма последовательности (Mermaid или PlantUML).
- Результаты работы (скриншоты, вывод тестов) SHOULD сохраняться для отчёта по мере
  реализации.

**Обоснование:** отчёт требует UML, листинги с комментариями и результаты работы. Собирать
их по ходу дешевле, чем в конце.

### VIII. Обязательная структура и порядок файлов (NON-NEGOTIABLE)

**Структура репозитория (монорепо).** Новые папки верхнего уровня MUST NOT появляться без
поправки к конституции.

```text
/                          корень монорепо
├── docker-compose.yml     вся инфраструктура
├── .env.example           все переменные окружения с комментариями (без секретов)
├── package.json           npm workspaces: backend, frontend, shared
├── backend/               NestJS
├── frontend/              Next.js
├── shared/                общие типы и DTO-контракты (только типы, без логики)
├── docs/                  отчёт: uml/, sequence/, screenshots/, report/
├── specs/                 артефакты Spec Kit (NNN-название-фичи/)
└── .specify/              служебные файлы Spec Kit
```

**Бэкенд.** Слои MUST зависеть только сверху вниз: `modules` → `infrastructure` → `core`.
Обратные импорты (например, `core` импортирует из `modules`) запрещены.

```text
backend/
├── prisma/                schema.prisma, migrations/, seed.ts
├── src/
│   ├── core/              ООП-ядро (принцип I), чистый TypeScript
│   │   ├── exceptions/    custom.exception.ts, not-found.exception.ts, ...
│   │   ├── collections/   linked-list.ts, priority-queue.ts, repository.interface.ts
│   │   ├── iterators/     iterator.interface.ts, stage-iterator.ts, ...
│   │   └── patterns/      command/, state/, observer/, strategy/, factory/, proxy/, singleton/
│   ├── infrastructure/    адаптеры: prisma/, storage/ (MinIO), queue/ (BullMQ), ffmpeg/,
│   │                      realtime/ (Socket.IO gateway), logger/
│   ├── common/            filters/, guards/, decorators/, pipes/ (сквозное для NestJS)
│   ├── modules/           по одной папке на предметную область
│   │   └── <module>/      auth, projects, boards, tasks, assets, versions, comments
│   ├── config/            загрузка и валидация конфигурации
│   ├── app.module.ts
│   └── main.ts
└── test/                  e2e-тесты
```

Каждый модуль MUST иметь одинаковый состав (лишние файлы не создаются):

```text
modules/<module>/
├── <module>.module.ts
├── <module>.controller.ts     HTTP: только приём запроса и вызов сервиса
├── <module>.service.ts        бизнес-логика
├── <module>.repository.ts     доступ к данным, реализует Repository<T>
├── dto/                       create-<entity>.dto.ts, update-<entity>.dto.ts
└── entities/                  доменные классы (не Prisma-модели)
```

**Фронтенд.**

```text
frontend/src/
├── app/                   маршруты Next.js (App Router): только страницы и layout
├── components/
│   ├── ui/                компоненты shadcn/ui (генерируются, вручную не правятся)
│   └── <feature>/         kanban/, player/, comments/, ...
├── features/              логика фич: хуки TanStack Query, api-клиенты, состояние
├── lib/                   утилиты, api-клиент, socket-клиент
└── styles/
```

**Именование.**
- Файлы и папки MUST быть в `kebab-case` с суффиксом роли: `tasks.service.ts`,
  `create-task.dto.ts`, `stage.iterator.ts`, `task.state.ts`.
- Классы, интерфейсы и типы — `PascalCase`. Интерфейсы MUST иметь префикс `I`
  (`IIterator<T>`, `ICommand`), как в лабах.
- React-компоненты — файлы в `kebab-case`, экспорт в `PascalCase` (`kanban-board.tsx` →
  `KanbanBoard`).
- Один публичный класс на файл. Тесты лежат рядом с кодом: `<имя>.spec.ts`.

**Порядок внутри файла.**
1. Импорты группами через пустую строку: сторонние пакеты → `@/core` → `@/infrastructure`
   и `@/common` → `@/modules` → относительные (`./`, `../`).
2. Типы и константы файла.
3. JSDoc класса (принцип VII), затем сам класс.

**Порядок членов класса.**
1. Статические поля → поля экземпляра (сначала `private readonly`).
2. Конструктор.
3. Публичные методы → защищённые → приватные.
4. Методы жизненного цикла (`onModuleInit`, `onModuleDestroy`, `dispose`) — в конце.

- Импорты из папок MUST идти через алиасы (`@/core/...`). Цепочки `../../../` глубже двух
  уровней запрещены.
- Каждая подпапка `core/` MUST иметь `index.ts`, который реэкспортирует её публичное API.

**Обоснование:** одинаковая структура позволяет за секунды найти нужный класс на защите,
упрощает листинги для отчёта и не даёт ООП-ядру смешаться с инфраструктурой.

## Технологические ограничения и предметная область

- **Язык:** TypeScript (strict mode) во фронтенде и бэкенде.
- **Фронтенд:** Next.js (React), Tailwind CSS + shadcn/ui, dnd-kit, TanStack Query,
  Video.js или hls.js.
- **Бэкенд:** NestJS, Prisma ORM, PostgreSQL.
- **Real-time:** Socket.IO. **Фоновые задачи:** BullMQ + Redis, FFmpeg (превью, прокси, HLS).
- **Файлы:** MinIO (S3-совместимое). Загрузка и скачивание MUST идти по presigned URL, без
  проксирования файлов через бэкенд.
- **Запуск:** вся инфраструктура MUST подниматься одной командой `docker compose up`.
  Образы MUST работать на Mac с Apple Silicon (arm64).
- **Домен:** проект → этапы (препродакшн, съёмка, монтаж, цвет, звук, сдача) → задачи →
  ассеты → версии (v1, v2, финал) → комментарии с таймкодом (`time_ms`; клик перематывает
  плеер).
- **Роли:** режиссёр, монтажёр, колорист, заказчик. Заказчик — гость с доступом только к
  ревью. Проверка прав MUST выполняться на бэкенде и при нарушении выбрасывать
  `AccessDeniedException`.
- **Язык документации:** русский (спецификации, планы, комментарии в ядре, отчёт).

## Процесс разработки и контроль качества

- Разработка идёт инкрементами MVP в этом порядке:
  1. авторизация, проекты, канбан с drag-and-drop;
  2. загрузка файлов в S3 + плеер;
  3. комментарии по таймкоду + версии;
  4. real-time и уведомления;
  5. FFmpeg-обработка (прокси, HLS, превью).
- Каждый инкремент проходит цикл Spec Kit: `specify` → (`clarify`) → `plan` → `tasks` →
  (`analyze`) → `implement`.
- Перед реализацией план MUST пройти проверку на соответствие принципам I–VIII
  (Constitution Check в `plan.md`).
- Новые файлы MUST создаваться строго по структуре принципа VIII; в `plan.md` раздел
  Project Structure MUST ссылаться на неё, а не придумывать свою.
- Инкремент считается готовым, когда тесты ядра проходят, приложение запускается через
  Docker Compose, а артефакты для отчёта (UML, диаграммы) обновлены.

## Governance

- Конституция имеет приоритет над остальными практиками и документами проекта.
- Изменения вносятся через `/speckit-constitution` с обновлением Sync Impact Report и версии.
- Версионирование — семантическое:
  - MAJOR — удаление или переопределение принципа;
  - MINOR — новый принцип или раздел, существенное расширение;
  - PATCH — уточнения формулировок.
- Отступление от принципа допускается только с письменным обоснованием в разделе
  Complexity Tracking соответствующего `plan.md`.
- Перед защитой MUST быть проведена финальная сверка кода с принципами I–VIII
  (`/speckit-analyze` по каждой фиче).
