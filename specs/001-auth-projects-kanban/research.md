# Research: Авторизация, проекты и канбан-доска

**Feature**: 001-auth-projects-kanban · **Date**: 2026-11-23

Каждое решение записано в формате «Решение → Почему → Что ещё рассматривали».
Неразрешённых вопросов (NEEDS CLARIFICATION) не осталось.

---

## R1. Среда выполнения и менеджер пакетов

- **Решение:** Node.js 24 LTS (уже установлен локально), TypeScript 5.x в режиме `strict`,
  npm workspaces: `backend`, `frontend`, `shared`.
- **Почему:** в конституции (принцип VIII) зафиксированы npm workspaces. Node 24 — текущая
  LTS-версия, есть сборки под arm64.
- **Что ещё рассматривали:** pnpm и Turborepo — быстрее, но это лишний инструмент, который
  пришлось бы объяснять на защите.

## R2. Аутентификация

- **Решение:** email + пароль. Хеш пароля — `argon2id`. После входа выдаются два JWT в
  httpOnly-cookie: access на 15 минут и refresh на 7 дней. Refresh-токен ротируется, его хеш
  хранится в БД, поэтому выход из системы реально отзывает сессию. Проверку делает
  `JwtAuthGuard` в NestJS, а WebSocket-соединение аутентифицируется по той же cookie при
  подключении.
- **Почему:**
  - httpOnly-cookie недоступна JavaScript на странице, поэтому её не украсть через XSS;
  - одна и та же cookie подходит и для HTTP, и для Socket.IO;
  - argon2 — текущая рекомендация OWASP.
- **Что ещё рассматривали:**
  - Сессии в Redis — Redis в этом инкременте больше ни для чего не нужен.
  - Auth.js/NextAuth — логика ушла бы во фронтенд, а исключения и права должны быть на
    бэкенде (принцип III, FR-011).
  - Хранить токен в localStorage — уязвимо к XSS.

## R3. Порядок карточек в колонке

- **Решение:** у задачи есть строковое поле `rank`, ключ дробной индексации (библиотека
  `fractional-indexing`). При вставке между карточками A и B вычисляется ключ между
  `rank(A)` и `rank(B)`. Остальные карточки не меняются.
- **Почему:** перемещение затрагивает одну строку в БД, поэтому одновременные перемещения
  разных карточек не конфликтуют. Отмена тоже меняет одну строку.
- **Что ещё рассматривали:**
  - Целочисленный `position` с перенумерацией колонки — каждое перемещение задевает N
    строк, и чаще возникают конфликты.
  - `float` — со временем теряется точность.

## R4. Конкурентные изменения

- **Решение:** оптимистическая блокировка. У задачи есть поле `version: int`, клиент
  передаёт `expectedVersion`. Если версии не совпали, сервер выбрасывает
  `ConflictException` (новый наследник `CustomException`, HTTP 409). Клиент получает
  актуальное состояние и откатывает карточку. При обычном перемещении правило «последний
  выигрывает» реализовано так: при конфликте клиент перечитывает данные и повторяет
  попытку один раз.
- **Почему:** это закрывает edge case «два участника двигают одну карточку» и FR-020
  (отмена отклоняется, если карточку уже изменил кто-то другой).
- **Что ещё рассматривали:** пессимистические блокировки — избыточно, и пришлось бы
  снимать блокировку при обрыве соединения.
- **Примечание к конституции:** `ConflictException` расширяет иерархию из принципа III,
  не нарушая её. Маппинг в 409 добавляется в тот же глобальный фильтр.

## R5. Отмена и повтор (паттерн Command)

- **Решение:** история команд хранится **на сервере**, в памяти. Ключ — `userId + projectId`,
  то есть у каждого пользователя своя история на каждой доске.
  - `MoveTaskCommand` реализует `ICommand` (`execute()` / `undo()`), то есть запоминает,
    откуда и куда переместили карточку.
  - `CommandHistory` хранит команды в своей коллекции `LinkedList<ICommand>` (принцип II):
    отмена и повтор — это движение по связному списку, глубина ограничена 50 шагами
    (FR-019). Новая команда после отмены отрезает «хвост» повторов.
  - Эндпоинты: `POST /projects/:id/board/undo` и `/redo`.
  - Неиспользуемые истории удаляются через 2 часа бездействия.
- **Почему:**
  - паттерн Command целиком живёт в `core/patterns/command`, и его показывают на защите;
  - сервер всё равно проверяет права и правила переходов (FR-020);
  - если сервер перезапустится, история пропадёт — это допустимо по спецификации
    («не сохраняется между сеансами»).
- **Что ещё рассматривали:** история на клиенте — тогда Command оказался бы во фронтенде,
  вне ООП-ядра, а повтор всё равно требовал бы серверной проверки.

## R6. Правила переходов (паттерн State)

- **Решение:** для каждого этапа есть свой класс-состояние. Все они наследуют абстрактный
  `StageState`: `PreproductionState`, `ShootingState`, `EditingState`, `ColorState`,
  `SoundState`, `DeliveryState`. Каждое состояние само знает, на какие этапы из него можно
  перейти (`allowedTransitions()`):
  - вперёд — на любой следующий этап, кроме «Сдача»;
  - назад — на любой предыдущий;
  - `ColorState` и `SoundState` дополнительно разрешают переход в «Сдача».
  
  Контекст `TaskStageContext.transitionTo(target)` при недопустимом переходе выбрасывает
  `ValidationException` с кодом `STAGE_TRANSITION_FORBIDDEN` и перечнем допустимых этапов.
- **Почему:** правила спецификации (FR-017, вариант B) записаны в одном месте и легко
  покрываются юнит-тестами (6 × 6 = 36 пар). Это классический State без `switch`.
- **Что ещё рассматривали:** таблица переходов `Map<Stage, Stage[]>` — проще, но паттерна
  State не показывает.

## R7. Типы задач (Factory Method)

- **Решение:** абстрактный `TaskCreator` с фабричным методом `createTask(data)` и
  наследники: `ShootingTaskCreator`, `EditingTaskCreator`, `ColorTaskCreator`,
  `SoundTaskCreator`, `GraphicsTaskCreator`, `OtherTaskCreator`. Каждый создаёт доменный
  класс своего типа (наследник `Task`) со значениями по умолчанию. Например, задача
  «съёмка» по умолчанию создаётся в этапе «Препродакшн», «цвет» — в этапе «Цвет».
  `TaskCreatorRegistry` выбирает нужного создателя по типу задачи.
- **Почему:** тип задачи из спецификации — естественное место для фабричного метода. В
  следующих инкрементах у типов появится разное поведение (например, только задача
  «монтаж» будет требовать версию видео).

## R8. Синхронизация доски (паттерн Observer)

- **Решение:**
  - После каждой успешной операции с задачей сервис публикует событие в `BoardEventBus`
    (Subject из `core/patterns/observer`).
  - На события подписаны наблюдатели:
    - `SocketBoardObserver` (в `infrastructure/realtime`) рассылает событие в
      Socket.IO-комнату `project:{id}`;
    - `AuditLogObserver` пишет событие в лог через Singleton-логгер.
  - Клиент применяет пришедшее событие к кешу TanStack Query.
  - Если соединение пропало (`socket.disconnected`), включается `refetchInterval: 60_000`
    и показывается индикатор «Нет связи» (FR-022). При переподключении данные доски
    сразу перезапрашиваются.
  - Изменения состава участников тоже идут событиями. Удалённого участника сервер
    отключает от комнаты и отправляет ему событие `member:removed` (FR-023).
- **Почему:** Observer отвязывает доменную логику от транспорта. Сервис не знает о
  Socket.IO, и сюда же без правок в сервисах подключатся уведомления из инкремента 4.
- **Что ещё рассматривали:**
  - Только опрос сервера (polling) — не укладывается в SC-007 (2 секунды).
  - Server-Sent Events — однонаправленные, а Socket.IO уже выбран в конституции.
  - Redis-адаптер для Socket.IO — нужен только при нескольких экземплярах бэкенда, вне
    рамок.

## R9. Итераторы и свои коллекции в этом инкременте

- **Решение:**
  - `StageIterator` — обход этапов вперёд или назад (`direction: 'forward' | 'backward'`).
    Используется в `StageState.allowedTransitions()`: последующие этапы получаются обходом
    вперёд, предыдущие — назад.
  - `DeadlineIterator` — обход задач в порядке дедлайна поверх `PriorityQueue<Task>`.
    Используется при загрузке доски: формирует список просроченных задач `overdue`
    (FR-015) в порядке срочности.
  - Оба реализуют `IIterator<T>` и `[Symbol.iterator]`. Вызов `next()` за концом коллекции
    выбрасывает `CustomException` с кодом `ITERATOR_EXHAUSTED`, на пустой коллекции — с
    кодом `ITERATOR_EMPTY`.
  - `Repository<T>` — общий интерфейс, его реализуют `UsersRepository`,
    `ProjectsRepository`, `TasksRepository`.
- **Почему:** принцип II требует использовать коллекции в живой логике, а принцип VI
  требует два итератора. Оба итератора здесь решают реальные задачи спецификации.

## R10. Singleton-логгер

- **Решение:** `AppLogger.getInstance()` в `core/patterns/singleton`. Логгер реализует
  интерфейс `LoggerService` из NestJS через тонкий адаптер в `infrastructure/logger` и
  подключается через `app.useLogger`.
- **Почему:** так требует таблица из принципа V, а ядро при этом не зависит от NestJS
  (принцип I).

## R11. Фронтенд

- **Решение:**
  - Next.js 15 (App Router), React 19, Tailwind CSS 4, shadcn/ui;
  - `@dnd-kit/core` + `@dnd-kit/sortable` для перетаскивания;
  - TanStack Query v5 с оптимистичными обновлениями;
  - `socket.io-client`.
  
  Права проверяются и на клиенте: заказчику не показываются элементы редактирования, а
  dnd-kit для него отключён. Сервер при этом проверяет права всегда (FR-011).
- **Почему:** стек зафиксирован в конституции. dnd-kit поддерживает и сортировку внутри
  колонки, и перенос между колонками, а также работу с клавиатуры.

## R12. Тестирование

- **Решение:**
  - бэкенд: Jest (стандарт NestJS);
    - юнит-тесты ядра без БД (принцип I);
    - интеграционные тесты модулей через Supertest на тестовой БД PostgreSQL;
  - фронтенд: Vitest + Testing Library для хуков и компонентов;
  - сквозные тесты: Playwright, 2–3 сценария из quickstart.md.
- **Почему:** юнит-тесты ядра — требование конституции. Playwright даёт скриншоты для
  отчёта (принцип VII).

## R13. Инфраструктура и запуск

- **Решение:** `docker-compose.yml` в этом инкременте поднимает `postgres:16`, `backend` и
  `frontend`. Redis и MinIO добавятся в инкрементах 2 и 5, когда появится в них
  необходимость. Все образы мультиархитектурные, работают на arm64.
- **Замечание:** Docker на машине пока **не установлен** (`docker: command not found`). Его
  нужно поставить (Docker Desktop или OrbStack для Apple Silicon) до первого
  `docker compose up`. Писать и тестировать ядро можно и без Docker.
